RESILIENCE, TESTED LIVE

Records survive outages on two paths

Explorer down 25 s

  1. Two uploads succeed anyway (HTTP 200)
  2. HTTP forward gives up after 5 retries
  3. Broker holds both for the explorer's session
  4. Delivered on restart, then confirmed

PostgreSQL down 25 s

  1. Upload succeeds; ingest answers 500
  2. HTTP forward gives up
  3. MQTT acknowledges only once stored, and retries
  4. Stored when the database returns, confirmed

Evidence: reports/mqtt/ (explorer and database outage runs on the real node). Ingest is idempotent: the second path is a no-op.

Explorer downtime never blocks an upload. We tested two outages live. With the explorer down, the HTTP forward gave up, but the broker kept the records for the explorer's persistent session and delivered them on restart. With the database down, MQTT only acknowledged a record once it was stored, so nothing was lost. Both paths are idempotent, so duplicates are harmless.
